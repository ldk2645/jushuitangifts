## 已确认原因及修复

真实 Selenium 检查发现班牛列表启用横向虚拟列。在固定 1440×900 视口下，初始 DOM 只有部分列，订单号列尚未渲染。原代码在筛选前要求同时读到订单号与创建时间，因而把可正常筛选的页面判为“列表尚未加载完成”。该问题已在真实页面复现，不是仅凭浏览器缩放作出的推测。

修复后先确认工作表、按钮和遮挡状态，再执行一次精确筛选。仅确认此次筛选刷新后，才有界滚动已核对的主表容器；最终仍要求同一 DOM 快照中同时读到订单号和创建时间、连续读取稳定、任务 ID 唯一且条数与分页一致。错订单、旧结果、缺列、结果超过一页仍停止，不把多次滚动的内容拼接成基线。

滚动可能重建表格行，因此礼品搜索结果和任务详情入口在首次点击前重新按身份查找。礼品必须再次核对首行编码和名称；任务必须同时匹配任务 ID 与订单号。实际原生点击仍只执行一次，点击异常不重试。这修复了隔离页面复现的滚动后旧元素失效；历史填写异常的具体触发位置未保存，本次不能断言全部 13 个属于同一原因。

重登安全检查此前复用“聚水潭首次查询失败”提示，即使异常来自班牛列表核查。现已改为独立的“失败订单重登安全核查未通过”，不影响安全判定，也不修改旧记录。
